# 外国籍アルバイトロールと週28時間上限 設計書

作成日: 2026-08-02

## 背景

店舗に外国籍のアルバイトがいる。資格外活動許可で働く在留資格（留学・家族滞在）の人は、
入管法上 **1週間28時間以内** しか働けない。これを超えると本人の在留資格が取り消されうるだけでなく、
雇用主も不法就労助長罪（入管法73条の2）の対象になり、懲役刑を含む罰則がある。

現状のアプリはロールごとの労働制約として「学生アルバイト（`student`）＝月80時間上限」を持っているが、
**週単位の上限を持つ仕組みが一切無い**。月上限だけでは、月の前半に集中して働かせる組み方が素通りする。

## 目的

`staffs.role` に「外国籍アルバイト」を追加し、そのロールのスタッフには週28時間の上限を
自動生成・手動入力の両方で効かせる。既存の `student` ロールと同じ作り・同じ手触りに揃える。

## 決定事項

ブレインストーミングで確定した内容。

| 論点 | 決定 | 理由 |
|---|---|---|
| 上限の結びつけ方 | **ロール＝週28h固定**。個別設定で緩められない | 週28hは法令上の固定値。店長が画面から緩められる余地を作らない。制限のない在留資格（永住者・定住者・日本人配偶者等）の人は従来どおり `part_time` で登録する運用 |
| 「1週間」の数え方 | **任意の連続7日間** | 入管の運用は「どの曜日から起算しても1週間28時間以内」。暦週（月曜起算）だと、前の週の後半に28h・次の週の前半に28h ＝ 連続7日間で56h という組み方が素通りする |
| 長期休業期間の特例 | **入れない**（常に週28h） | 在籍校ごとに休業期間が異なり、スタッフ別の期間管理が必要になる。安全側に倒す。必要になった時点で「週上限を期間で切り替える」形で追加する |
| 学生ルールの重ねがけ | **重ねない**（週28hのみ） | 月80hは週換算で約18.6hであり、重ねると週28hの判定がほぼ発火せず実装の意味が消える。学業配慮が必要な人は、その人の月上限（`max_hours_per_month`）を個別に下げれば済む（既存機能） |
| 自動生成が上限にぶつかったとき | **配置しない**（結果は人員不足として表示） | 学生の月80h上限と同じ振る舞い。店長から見た挙動が一貫する |
| 手動入力が上限を超えるとき | **確認ダイアログを出して強行可能**。承諾は記録に残す | 在留資格の変更直後など、アプリが把握していない事情がありうる。ただし後から在留資格の照会を受けたときに店長が説明できるよう、承諾したシフトには印を残す |

## スコープ外

- 在留資格の種別・在留期限・資格外活動許可の有無をアプリで管理すること（在留カードの管理機能に踏み込む）
- 長期休業期間の週40時間特例
- 既存 `student` ロールへの週上限の適用（今回は `foreign_worker` のみ）
- 過去に登録済みのシフトの遡及チェック（今回入れるのは登録時点の検査のみ）

## 設計

### 1. ロール定義

`role` の値に **`foreign_worker`** を追加する。表示名は「外国籍アルバイト」。
既存が `student`＝「学生アルバイト」なので、同じ1語の粒度に揃える。

```sql
CHECK(role IN ('employee','part_time','manager','student','foreign_worker'))
```

- `schema.sql` の CHECK 制約を更新
- `migrations/0007_add_foreign_worker_role.sql` を新設する（既存の最新は `0006`）

マイグレーションは `staffs` テーブルの再構築になる（SQLite は CHECK 制約を後から変更できない）。
`migrations/0004_fix_student_role_check.sql` が「`0003` が部分適用で終わった事故のやり直し」であることを踏まえ、
**再構築の全手順を1ファイルで完結させ、途中で失敗しても中途半端な状態が残らない順序**にする。
`src/migrator.py` の `LEGACY_FILES` には追加しない（0007 は通常のマイグレーションとして適用される）。

**承諾フラグ用のカラムを同じマイグレーションで追加する**:

```sql
ALTER TABLE shifts ADD COLUMN weekly_cap_ack INTEGER DEFAULT 0;
```

既存の `over_cap_flag INTEGER DEFAULT 0`（必要人数超過の枠に重なる確定シフトの印）と同じ形。
`ALTER TABLE ... ADD COLUMN` は `src/migrator.py` が既に扱える構文。

### 2. 週28時間の判定（`src/weekly_hours.py` 新規）

外部依存の無い純関数モジュールとして切り出す。`src/name_match.py` と同じ方針。

**なぜ切り出すか**: 週28hの判定は自動生成（`shift_engine.py`）と手動入力（`app.py`）の両方で必要になる。
エンジン内に直接書くと API 側で同じ計算を書き直すことになり、片方だけ直して食い違う。

インターフェース:

```python
WEEKLY_CAP_MINUTES = 28 * 60

def minutes_by_day(shifts):
    """シフト列 → {"YYYY-MM-DD": 実働分} に畳む。

    日をまたぐシフト（22:00〜翌6:00）は日付ごとに分割して計上する。
    """

def exceeds_weekly_cap(day_minutes, target_day=None, cap_minutes=WEEKLY_CAP_MINUTES):
    """連続7日間の合計が cap を超える窓があれば (窓の開始日, 窓の終了日, 合計分)
    を返す。無ければ None。

    target_day を渡すとその日を含む7通りの窓だけを調べる（シフトを1件足すときの判定）。
    省略すると全期間の窓を調べる（生成結果全体の検証）。
    超過する窓が複数ある場合は、合計が最大の窓を返す（店長には最も厳しい窓を見せる）。
    """
```

判定の中身は7日窓（開始日 = 対象日の6日前 〜 対象日）を順に調べる素朴なループ。
1件追加の判定なら7窓、1か月分の検証でも高々31×7回で、最適化は不要。

**調べる窓の範囲**: シフトを1件足すときは、その日を含む7通りの窓だけを見れば足りる。
それ以外の窓の合計はこのシフトによって変わらないため。

**日またぎの計上**: 労基・入管が見るのは実労働時間なので、日をまたぐシフトは各日に分けて数える。
`shift_engine.py` は既に日またぎシフトを扱っており（`end_iso[:10] != day` の分岐）、
数え方を揃えないと生成と検証で結果がズレる。

**休憩時間**: `shifts.break_time_minutes` を実働から差し引く。28hは実労働時間の上限であり、
休憩を含めて数えると本来働ける時間を不当に削ることになる。

### 3. 自動生成（`src/shift_engine.py`）

`auto_generate(shop_id, settings, start_date, end_date)` に次を足す。

1. **生成範囲の6日前からの確定シフトを読み込む**（`from db import query_all` は既にある）。
   これが無いと、月初の週に対する7日窓が前月末を見落とし、月をまたいだ超過が素通りする。
   読み込んだ分は「既に働いた実績」として窓の合計に入れるだけで、配置対象にはしない。
2. `can_place()` に週上限チェックを追加する。`foreign_worker` のスタッフについてのみ、
   そのシフトを足したときに超過する窓があれば配置しない（理由コード `weekly_cap`）。
   既存の理由コード（`rest_request` / `min_daily` / `max_daily` / `already_working`）と同じ形。
3. `post_validate` 相当の箇所で、確定結果に週超過が残っていないかを検証し、
   残っていれば警告に積む（`{"type": "weekly_cap_overflow", ...}`）。
   既存の `monthly_overflow` と同じ形の二重の安全弁。

配置されなかった枠は既存の不足（shortage）としてそのまま画面に出る。新しい表示は足さない。

### 4. 手動入力（`src/app.py`）

シフトの作成・更新・移動の3箇所（現在 `_check_student_only_shift` を呼んでいる箇所と同じ）に
週上限チェックを足す。

- 超過する場合は 400 を返し、ボディに `{"weekly_cap_exceeded": true, "detail": {...}}` を含める。
  既存の `{"student_only": true}` と同じ作法（`tests/test_integration_flow.py` がこの形を固定している）
- `detail` には超過した窓の期間と合計時間を入れる。店長が「どの7日間が何時間になるのか」を
  ダイアログで読めなければ判断できない
- リクエストボディに `weekly_cap_confirmed: true` があれば通す。
  そのとき保存するシフトの `weekly_cap_ack` を 1 にする

**承諾の記録**: `weekly_cap_ack=1` のシフトは、店長のシフト一覧・印刷で見分けられるようにする
（既存の `over_cap_flag` と同じ扱い）。誰がいつ承諾したかは、シフトの `updated_at` と
操作者が店長であることから追える（このアプリのシフト編集は店長ロールに限られる）ため、
専用の監査テーブルは作らない。

**チェックの対象**: `staffs.role = 'foreign_worker'` のスタッフのみ。他ロールの挙動は1バイトも変えない。

### 5. スタッフ登録・編集 API

`foreign_worker` を許可する値に加える。現在 `("employee", "part_time", "manager", "student")` を
列挙している箇所すべて:

- `src/app.py` — スタッフ作成（1806行付近）
- `src/admin_api.py` — ロール変更（556行付近）、スタッフ編集（618行付近）、スタッフ作成（803行付近）

`student` の月80h強制のような特別扱いは `foreign_worker` には無い（週上限はロールから自動で効くため、
`max_hours_per_month` の既定値は `part_time` と同じ160のままでよい）。

`src/admin_api.py:743` の `"supports_student_role": "student" in schema.lower()` と同じ形で、
本番DBのスキーマが古い場合の検出も追加する（0007 未適用のD1に対して500ではなく明示的なエラーを返すため）。

### 7. テスト

- **`tests/test_weekly_hours.py`** — 純関数の境界値
  - 27.9h / ちょうど28.0h / 28.1h

  - 日をまたぐシフトが日付ごとに分割計上されること
  - 休憩時間が実働から引かれること
- **`tests/test_foreign_worker_role.py`** — API とエンジン

  - 手動追加が400と `weekly_cap_exceeded` を返す

- **E2E** — 手動追加の確認ダイアログと強行、ロールの色・ラベル表示

## 既知の制約・リスク

- **在留資格を見ていない**。ロールを付けるかどうかは店長の判断に委ねられる。永住者のように制限のない
  外国籍スタッフを `foreign_worker` にすると、不要な28h上限がかかる（運用で `part_time` を使う）
- **過去分は遡及チェックしない**。0007 適用前に登録済みのシフトは、28hを超えていても警告されない
- **`weekly_cap_confirmed` による強行を許す**以上、違法就労のシフトがアプリに保存されうる。
  `weekly_cap_ack` の印が唯一の手がかりになる
- **スタッフ一覧の並び順が変わる**。`ORDER BY role DESC` のため `foreign_worker` は
  `employee` と `manager` の間に入る。既存テストが並び順に依存していないか確認が必要
