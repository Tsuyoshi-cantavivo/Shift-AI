# 希望テキスト取り込み 設計書

日付: 2026-07-26
状態: 設計確定（実装計画の作成待ち）

## 1. 目的

店長が、スタッフから受け取ったテキスト（LINE のメッセージ、口頭を書き起こしたメモなど）を貼り付けるだけで、シフト希望として登録できるようにする。

### 背景

エスフォルタ渋谷店（`Esforta`）は仮運用中で、スタッフ11名（店長1・社員3・パート2・学生5）の希望を**店長がすべて代理で入力したい**という要望がある。

現在、希望を登録できるのは次の2経路のみで、いずれも**本人しか登録できない**。

- `POST /api/shop/my-requests` — 店長が自分の希望を出す
- `POST /api/staff/requests` — スタッフが自分の希望を出す

店長が他人の希望を登録する経路は存在しない。11名分を手入力するには、そもそも入力する場所がない。

### なぜテキスト取り込みを最初に作るか

手入力用のマトリクス UI（Phase 2）より先に作る。理由は、11名×1ヶ月を手で打ち込む作業そのものを無くせるため。入力の「場所」を作るより、入力を「しなくて済む」ようにする方が効果が大きい。

テキスト取り込みができれば、手入力の口が無くても実運用は回る（店長がテキストを打てば取り込める）。

## 2. 決定事項

| 項目 | 決定 | 根拠 |
|---|---|---|
| 着手順 | テキスト取り込み → マトリクス入力 → 前月コピー → 傾向提示 | 入力負荷の削減効果が最大のものから |
| 受け取り方 | 個別・グループ両対応 | 実際に両方あるため。スタッフ指定は任意にする |
| 確認画面 | **月間カレンダー**に解析結果を戻して見せる | 1人が1ヶ月分20〜30件を送ってくる。表では1画面に収まらない |
| 誤読の扱い | **必ず人が確認してから登録** | AI は誤読する。「8/3」を「8月3週」と読む類の取り違えが確定シフトに流れると事故になる |
| 既存希望 | **消さない。追加のみ** | テキスト解析の誤りが既存データを壊すのが最も避けたい事故 |
| 判定不能分 | **登録しない。「未割り当て」として保留** | AI が推測で誰かに割り当てるより、人に渡す方が安全 |
| 「学習」の定義 | **個人の傾向を提示するのみ**（自動では入れない） | Phase 4。AI が希望を生成するのは別プロジェクト |

## 3. データの保存先

**既存の希望提出と同じく、`shifts` と `wish_history` の両方に保存する。**

`POST /api/staff/requests`（`src/app.py:3339`）の実装がそうなっており、片方だけでは機能しない。

| テーブル | 役割 | 入れないとどうなるか |
|---|---|---|
| `shifts`（`status='requested'`） | AI シフト生成の入力 | 取り込んだ希望が AI 生成に反映されない |
| `wish_history` | 永久履歴。希望表管理画面が読む | 希望表管理画面に出ない。確定後に希望が消える |

既存実装の作法も踏襲する。

- `wish_history` は `(staff_id, start_datetime, end_datetime)` が同一なら INSERT をスキップ（二重登録防止）
- `shifts` は同一スタッフ・同日時間帯の重複をスキップし、件数を返す
- 休憩時間は `compute_break_minutes(work)` で算出する

### `availability` の語彙と時刻の決め方

既存の値をそのまま使う。データモデルの変更は不要。

**時刻の決め方は既存実装（`src/app.py:3339` の `/api/staff/requests`）に合わせる。**

| 値 | 意味 | `start_datetime` | `end_datetime` |
|---|---|---|---|
| `rest` | 休み希望 | `{date}T00:00:00` | `{date}T23:59:59` |
| `any` | いつでも可 | `{date}T09:00:00` | `_get_shop_shift_end_time()` の値 |
| `morning` | 早番希望 | `{date}T09:00:00` | 〃 |
| `evening` | 遅番希望 | `{date}T09:00:00` | 〃 |
| `time` | 時間指定 | 指定された `start` | 指定された `end`（`end <= start` なら翌日扱い） |

`any` / `morning` / `evening` が同じ時刻になるのは既存の挙動どおり。区別は `availability` の値が担っており、時刻は担っていない。ここを変えると既存データとの整合が崩れるため、揃える。

**`rest` の扱いに注意。** スタッフの希望提出 UI（`app.js:3596`）は `if (w.type === 'rest') return;` で休み希望を**送信していない**。しかし API 上は登録でき、希望表管理画面は `.wmark.rest` で「休」を表示する。今回の取り込みでは**休み希望を登録する**（「8/3は休みたい」を取りこぼさないため）。

### 募集期間と締切の扱い

既存の `/api/staff/requests` は次の2つを検証し、外れていれば 400 を返す。

```python
period = query_one("SELECT * FROM shift_request_periods WHERE shop_id=? AND is_active=1 AND start_date<=? AND end_date>=? ...")
if not period: abort(400, "この日程は募集期間外です")
if period["deadline"] < jst_today(): abort(400, f"締切（{period['deadline']}）を過ぎています")
```

**店長の代理入力ではこの2つを適用しない。**

- **締切**はスタッフに対する期限であって、店長を縛るものではない。「締切後に LINE で届いた希望を店長が入れる」は正当な運用
- **募集期間**が未設定の店舗でも取り込めるようにする

ただし期間外の日付が含まれる場合は、**プレビューで警告を出す**（登録は妨げない）。店長が意図せず翌々月の日付を登録してしまう事故を防ぐため。

### 重複の扱い

既存と同じく `_check_staff_overlap(shop_id, staff_id, start, end, include_requested=True)` を使い、同一スタッフの同日で時間帯が重なる希望・確定シフトがあればスキップする。スキップ件数は登録結果に含めて返す。

## 4. 解析

### 既存資産

`src/ai.py` に LLM 基盤がある。**そのまま使う。**

- `call_llm(system_prompt, user_prompt, temperature)` — OpenAI 互換 API を叩く（既定 `gpt-4o-mini`）
- `is_llm_available()` / `get_last_llm_error()` — 未設定時の判定
- `_parse_explicit_time_range(text)` — 「13-18」「17時まで」等から時刻範囲を抽出
- `_parse_request_fallback(...)` — LLM が使えない環境での正規表現ベースの解析

### 新設する関数

既存の `parse_shift_request()`（`src/ai.py:274`）は**流用しない**。あれは「月8万円稼ぎたい」という**収入目標**から必要日数を逆算して提案する関数で、出力が `need_hours` / `ng_weekdays`（曜日）ベースであり、「8/3は休み」のような**特定日付**を表現できない。

新たに `parse_wish_text(text, year_month, staff_names)` を作る。

**入力**
- `text` — 貼り付けられた生のテキスト
- `year_month` — 対象月（`"2026-08"`）。相対表現（「来週」「月末」）の解決に使う
- `staff_names` — その店舗のスタッフ名の一覧。誰の希望かの判定に使う

**出力**

```json
{
  "entries": [
    {
      "staff_hint": "小久保",
      "dates": ["2026-08-03", "2026-08-10"],
      "availability": "rest",
      "start": null,
      "end": null,
      "raw": "8/3と8/10は休みたいです"
    },
    {
      "staff_hint": null,
      "dates": ["2026-08-04", "2026-08-06", "2026-08-08"],
      "availability": "time",
      "start": "17:00",
      "end": "22:00",
      "raw": "月水金の夕方なら入れます"
    }
  ],
  "unparsed": ["読み取れなかった文"],
  "source": "llm" | "fallback"
}
```

**設計の要点**

- **同じ内容の日は `dates` にまとめ、内容が違えば `entries` を分ける。** 「土日は休み、平日は17時から」なら2エントリ。「8/1 9-17、8/3 13-22」のように日ごとに違えば日数分のエントリになる
- **`raw` を必ず持たせる。** プレビューで「この文をこう読みました」と対比させるため。これが無いと店長は解釈の正否を判断できない
- **`staff_hint` は名前の断片でよい。** サーバ側でスタッフ名と突き合わせる。一致しなければ `null` として未割り当てに送る
- **`unparsed` に残った文は捨てない。** 画面に表示して、店長が手で入力できるようにする

### フォールバック

`is_llm_available()` が偽のとき、または LLM 呼び出しが失敗したときは、正規表現ベースの簡易解析に落とす。

- 日付: `8/3`、`8月3日`、`8/3〜8/5`、`8/3,8/5,8/7`
- 時刻: 既存の `_parse_explicit_time_range()` を使う
- 休み: 「休」「不可」「NG」「無理」を含む行
- 全可: 「終日」「いつでも」「フル」

フォールバック時は `source: "fallback"` を返し、画面に「簡易解析で読み取りました。内容をよく確認してください」と出す。**LLM が無くても機能が死なないようにする**（本番で `LLM_API_KEY` が未設定でも使える）。

## 5. API

### `POST /api/shop/wishes/parse`

テキストを解析する。**保存は一切しない。** 何度でも試せる。

```
リクエスト  { "text": "...", "year_month": "2026-08", "staff_id": 3 | null }
レスポンス  { "entries": [...], "unparsed": [...], "source": "llm" }
```

`staff_id` を指定した場合は、その人の希望として解析する（`staff_hint` を無視して全エントリに `staff_id` を割り当てる）。指定しない場合は `staff_hint` から推定する。

権限: `shop` ロールのみ。

### `POST /api/shop/wishes/bulk`

プレビューで確定した内容を一括登録する。

```
リクエスト  {
  "wishes": [
    { "staff_id": 3, "date": "2026-08-03", "availability": "rest",
      "start": null, "end": null, "raw": "8/3は休みたいです" }
  ],
  "overwrite": false
}
レスポンス  { "ok": true, "created": 12, "skipped": 3, "message": "12件を登録しました（3件は既存のためスキップ）" }
```

- `wishes` は**日付ごとに1件**に展開済みのものを受け取る（`dates` の配列はクライアント側で展開する）。サーバ側の処理を単純にするため
- `overwrite: false`（既定）— 同じ `(staff_id, date)` に既存の希望があればスキップ
- `overwrite: true` — 既存を削除してから登録する。**店長がプレビューで明示的に選んだ場合のみ**
- `note` には `"店長が取り込み: {raw}"` を入れる。後から「本人が出した希望か、店長が代理で入れたものか」を区別できるようにする

権限: `shop` ロールのみ。

### 既存 API の変更

**なし。** 既存の `/api/shop/my-requests`、`/api/staff/requests`、`/api/shop/wishes` は変更しない。

## 6. 画面

希望表管理（`SCREENS.requests`）に「**テキストから取り込む**」ボタンを追加し、モーダルで次の流れを提供する。

```
┌ ステップ1: 貼り付け ─────────────────────┐
│ 対象月  [2026年8月 ▼]                    │
│ スタッフ [自動判定 ▼]  ← 任意で指定できる  │
│ ┌──────────────────────────────────┐ │
│ │ LINEの文面をここに貼る                │ │
│ └──────────────────────────────────┘ │
│                        [解析する]        │
└──────────────────────────────────────┘

┌ ステップ2: 確認（カレンダー） ───────────┐
│ 小久保 ▼   ← スタッフを切り替える          │
│ ┌─┬─┬─┬─┬─┬─┬─┐                     │
│ │日│月│火│水│木│金│土│                     │
│ ├─┼─┼─┼─┼─┼─┼─┤                     │
│ │ │ │ │ │ │1│2│                     │
│ │3│4│5│6│7│8│9│  ← 3=休 4=17-22 …    │
│ └─┴─┴─┴─┴─┴─┴─┘                     │
│ 日付をクリック → その日の解釈と元の文を表示  │
│                                          │
│ ⚠ 未割り当て 2件                          │
│  「来週は月水金入れます」 [誰の希望か選ぶ▼] │
│                                          │
│                    [登録する] [やり直す]  │
└──────────────────────────────────────┘
```

**カレンダーのマスに出すもの**

- `rest` → 「休」
- `time` → 「17-22」
- `any` → 「終日」
- `morning` / `evening` → 「早」「遅」
- 既存の希望がある日 → 印を付け、クリック時に「既存あり。上書きしますか」を出す

**色は既存のトークンを使う。** 新しい色を作らない。既存の `.wmark` の語彙（`any` / `morning` / `evening` / `rest` / `time`）がそのまま使える。

**日付マスのクリックで開く詳細**

```
8月3日（月）
  読み取り: 休み希望
  元の文  : 「8/3と8/10は休みたいです」
  [休み ▼] [削除]
```

元の文を必ず見せる。これが誤読を発見する唯一の手段になる。

## 7. 安全策

| リスク | 対策 |
|---|---|
| AI の誤読が確定シフトに流れる | 登録前に必ずカレンダーで確認させる。`parse` は保存しない |
| 既存の希望を壊す | 既定で上書きしない。上書きは店長が明示的に選んだときのみ |
| 誰の希望か誤判定 | 一致しなければ未割り当てにして人に渡す。推測で割り当てない |
| LLM が使えない環境で機能が死ぬ | 正規表現フォールバックを用意し、`source` を画面に出す |
| 代理入力と本人入力が区別できない | `note` に「店長が取り込み」と元の文を残す |
| 大量データの誤登録 | 登録結果に件数を返し、「12件を登録（3件スキップ）」と明示する |

## 11. 前提として確認済みの事実

- `wish_history` は `(id, shop_id, staff_id, start_datetime, end_datetime, availability, submitted_at, note)`
- 既存の希望提出は `shifts`（`status='requested'`）と `wish_history` の両方に INSERT する（`src/app.py:3339` 付近）
- `wish_history` は `(staff_id, start_datetime, end_datetime)` の重複を INSERT 前にチェックしている
- `/api/staff/requests` は募集期間（`shift_request_periods`）と締切を検証し、外れていれば 400 を返す
- `availability` 指定時の `end_datetime` は `_get_shop_shift_end_time(shop_id)` が決める
- スタッフの希望提出 UI は `rest`（休み希望）を送信していない（`app.js:3596` で捨てている）が、API 上は登録可能で、希望表管理画面は `.wmark.rest` で表示する
- `shifts` への INSERT 時、`availability` があれば `reason="スタッフ希望(柔軟)"`、無ければ `reason="スタッフ希望提出"` と休憩時間の計算が入る
- `src/ai.py` に LLM 基盤があり、OpenAI 互換 API（既定 `gpt-4o-mini`）を使う。`LLM_API_KEY` 未設定時のフォールバックも実装済み
- 希望表管理画面（`SCREENS.requests`）は `/api/shop/wishes` から `wish_history` を読む
- `availability` の語彙は `rest` / `any` / `morning` / `evening` / `time`
- Esforta のスタッフは11名（manager 1・employee 3・part_time 2・student 5）
