# スタッフの働き方の変化に気づく（気にかけたい人） 設計書

作成日: 2026-08-02

## 背景

ダッシュボードの「AIからの提案」（`POST /api/shop/ai/review` → `ai.review_shift_balance`）は、
指定期間の確定シフトだけを見て、連勤過多や労働時間の偏りを指摘する。見ているのは
**その月のスナップショット**であり、**過去と比べた変化**は見ていない。

そのため「いつもシフトに入っていた人が、最近急に少なくなった」「直前の変更・取消が続いている」
といった、**人が離れていく前の変化**に気づけない。気づけるのは店長が個別に思い出したときだけで、
気づいたときには手遅れ、ということが起こる。

## 目的

勤務データの変化を検出し、**店長が本人に声をかけるきっかけを早く作る**。

## スコープを明確に区切る

**このシステムは、スタッフの心の状態を判定しない。**

アプリが持っているのは勤務データだけで、そこから健康状態や離職の意思は分からない。
分かるのは「働き方が変わった」という事実だけである。それを健康状態の判定として見せると、
外れた決めつけを店長に渡すことになり、スタッフへの不利益（不当な評価、詮索）につながる。

したがって:

- 出すのは **事実（データがどう変わったか）** と **尋ね方の例** だけ
- 「離職しそう」「メンタルに問題がある」といった **原因や状態の断定は出力しない**
- 解釈と対話は店長に委ねる
- 画面には「変化には本人の希望や学業・家庭の事情など理由があります。決めつけずに伺ってください」
  を常に添える

## 決定事項

ブレインストーミングで確定した内容。

| 論点 | 決定 | 理由 |
|---|---|---|
| 検出する変化 | **出勤量の減少** と **直前の変更・取消の増加** の2つ | いまのデータ（`shifts` / `change_requests`）から確実に取れる。時間帯の変化・希望の出し方は今回入れない |
| 判定期間 | **直近30日 対 その前の60日** | 月の区切りに依存しないため、月初に「今月はまだ出勤が少ない」という誤検知が起きない。変化が起きてから気づくまでが最も早い |
| 見せ方 | **該当者がいるときだけ**ダッシュボードに別枠で出す | 毎回何か出ると見流される。出ること自体に意味を持たせる。個人名を出すので既存の全体アドバイスとは分けて扱う |
| 文言の生成 | 検出はルール、**声かけの言い回しだけ LLM** | 数値比較をLLMに委ねると不安定。既存 `review_shift_balance` と同じくLLM未接続時は定型文へフォールバック |

## スコープ外

- 働く時間帯の変化（早番→遅番など）の検出
- 希望の出し方の変化（休み希望の増加、未提出）の検出
- スタッフ本人への表示・通知
- 健康状態・離職意思の推定
- 検出条件の画面からの調整（しきい値は定数で持つ）

## 設計

### 1. 検出ロジック（`src/staff_attention.py` 新規）

外部依存の無い純関数モジュール。`src/name_match.py` / `src/weekly_hours.py` と同じ方針。

**なぜ切り出すか**: 判定は「何日から何日までを、どう数えて、どのしきい値で比べるか」の塊で、
DBアクセスやLLMと混ざると条件を変えたときの影響が読めなくなる。純関数なら境界値をテストで
固定できる。

インターフェース:

```python
RECENT_DAYS = 30          # 直近としてみる日数
BASE_DAYS = 60            # 比較の基準に使う、その前の日数
MIN_BASE_ATTENDANCE = 4   # 基準期間の30日あたり出勤日数がこれ未満の人は対象外
DROP_RATIO = 0.6          # 直近が基準の何倍を下回ったら「減った」とするか
MIN_RECENT_REQUESTS = 3   # 直近30日の変更・取消がこれ未満なら対象外
REQUEST_SPIKE_RATIO = 2.0 # 直近が基準の何倍以上なら「増えた」とするか

def find_attention(staff_rows, shift_rows, request_rows, today):
    """気にかけたいスタッフを返す。

    staff_rows:   [{"id", "name", "is_resigned"}]
    shift_rows:   [{"staff_id", "start_datetime"}]（確定シフトのみ）
    request_rows: [{"staff_id", "created_at"}]（変更・取消の申請）
    today:        "YYYY-MM-DD"

    戻り値: [{"staff_id", "name", "reasons": [...]}] を、変化の大きい順に返す。
    reasons の要素は次のいずれか:
      {"type": "attendance_drop", "recent": int, "base": float}
      {"type": "request_spike",   "recent": int, "base": float}
    """
```

**判定の中身**:

- 期間は `today` を末日とする直近30日（`today-29` 〜 `today`）と、その前の60日（`today-89` 〜 `today-30`）
- `base` は基準期間の件数を **30日あたりに換算**した値（60日の件数 ÷ 2）
- 出勤日数は「シフトのある日」を数える（同じ日に2本入っていても1日）

**出勤減少**（`attendance_drop`）:
- `base >= MIN_BASE_ATTENDANCE` かつ `recent < base * DROP_RATIO`

**変更・取消の増加**（`request_spike`）:
- `recent >= MIN_RECENT_REQUESTS` かつ（`base == 0` または `recent >= base * REQUEST_SPIKE_RATIO`）

**除外**:
- `is_resigned` のスタッフ
- 基準期間に1日も出勤がない人（入って間もない人。比べる過去がない）

**並び順**: 変化の度合いが大きい順。度合いは次で定義する（複数の理由を持つ人は最大値を採る）:

- `attendance_drop`: `1 - recent / base`（基準に対してどれだけ減ったかの比率。0〜1）
- `request_spike`: `min(1.0, recent / max(base, MIN_RECENT_REQUESTS) / REQUEST_SPIKE_RATIO)`
  （基準0件でも0除算にならず、比率として 0〜1 に収める）

同点は staff_id 昇順（表示順が実行のたびに入れ替わらないようにする）。

### 2. 声かけの文言（`src/ai.py` に追加）

```python
def suggest_attention_message(name, reasons):
    """検出結果から、店長が本人に尋ねるときの声かけ例を1つ返す。"""
```

システムプロンプトで次を明示的に禁じる:

- 原因の断定（離職・体調・人間関係など）
- 評価的な表現（やる気がない、責任感がない など）
- 本人に伝える前提の指示口調

出力させるのは「店長が本人に尋ねるときの一言」だけ。1〜2文。

LLM未接続時のフォールバック（既存 `review_shift_balance` と同じ二段構え）:

- 出勤減少: 「最近シフトが少なめですが、ご都合はいかがですか。入りたい曜日や時間が変わっていたら教えてください。」
- 変更増加: 「予定の変更が続いているようですが、無理のない範囲で組めていますか。組みにくい曜日があれば教えてください。」

### 3. API（`src/app.py`）

`POST /api/shop/staff-attention` を新設する。

- 認可: `_shop_ctx()`（店長のみ。既存のダッシュボードAPIと同じ）
- 入力: なし（サーバ側で今日を基準に期間を決める）
- 処理: 過去90日分の確定シフトと変更申請を読み、`find_attention` に渡す。
  検出された人ごとに `suggest_attention_message` で文言を付ける
- 出力:

```json
{
  "items": [
    {
      "staff_id": 12,
      "name": "田中太郎",
      "reasons": [{"type": "attendance_drop", "recent": 4, "base": 10.0}],
      "headline": "出勤が減っています",
      "detail": "以前は30日あたり10.0日 → 直近30日は4日",
      "message": "最近シフトが少なめですが、ご都合はいかがですか。"
    }
  ],
  "source": "llm"
}
```

**既存の `/api/shop/dashboard` には混ぜない。** ダッシュボードAPIは既に多くを返しており、
LLM呼び出しを含むこの処理を足すと、ダッシュボード全体の表示がLLMの応答時間に引きずられる。

### 4. 画面（`public/app.js`）

ダッシュボードの右カラム（`#dashRight`）、「AIからの提案」の**上**に「気にかけたい人」カードを置く。

- **`items` が空のときはカードごと出さない**（平常時は何も増えない）
- 1人ぶんの表示:
  - スタッフ名 + 見出し（「出勤が減っています」など）
  - 事実（`detail`）
  - 声かけの例（`message`）
  - 「シフトを見る」— そのスタッフで絞ったシフト画面へ
- カード末尾に固定文:
  「変化には本人の希望や学業・家庭の事情など理由があります。決めつけずに伺ってください。」

既存の「AIからの提案」と同様、取得失敗時はカードを出さない（ダッシュボードの他の部分を妨げない）。

### 5. テスト

- **`tests/test_staff_attention.py`** — 純関数の境界値
  - しきい値ちょうど（減少率 0.6 ちょうどは検出しない／下回れば検出する）
  - 基準が `MIN_BASE_ATTENDANCE` 未満の人は検出しない（月1〜2回の人を拾わない）
  - 退職者を検出しない
  - 基準期間に出勤がない新人を検出しない
  - 同じ日に2本シフトがあっても1日として数える
  - 並び順が減少幅の大きい順で、同点は安定していること
- **`tests/test_staff_attention_api.py`**（または既存APIテストに追加）
  - 店長以外は 401/403
  - 該当者がいなければ `items` が空
  - LLM未接続でも定型文が返る（`source` が `rule_based`）
- **E2E**
  - 該当者がいるときだけカードが出る（いないときは出ない）
  - 断定的な文言（「離職」「メンタル」）が画面に出ない

各テストは「守りたい実装の1行を消すと赤になる」ことを実出力付きで確認する。

## 既知の制約・リスク

- **勤務データしか見ていない**。本人が店長に相談済みの事情（学業・家庭）でも検出される。
  だからこそ画面で「決めつけずに伺ってください」と明示する
- **検出されないこと＝問題がないこと、ではない**。しきい値を下回る変化や、
  データに表れない不調は拾えない。この機能を見ていれば安心、という位置づけにはしない
- **しきい値は固定値**。店舗の規模や業態によって適切な値は変わるが、まずは既定値で運用し、
  必要になったら設定可能にする
- **店長が見る前提**の情報であり、スタッフ本人には表示しない。人事評価に使われると
  本来の目的（早く声をかける）から外れるが、これは運用側の問題として設計では扱わない
